# ADR 0025 — Scope change and stale requirement detection

## Status

Proposed.

## Context

The substrate already supports drift detection mechanically. The hash-chained `event_log` (tech-spec §4.6 lines 273–286) records every mutation; the 4-tier semantic AST diff ladder (tech-spec §3.2 lines 116–119) emits drift events on `onDidSaveTextDocument`; the verifier scheduler (tech-spec §3.4 lines 128–138; ADR-0016) re-runs obligations against changed nodes; PPR over the heterogeneous graph (tech-spec §3.7 lines 152–156) traverses `realizes`, `depends_on`, `syncs_with`, and `constrains` edges (tech-spec §4.2 lines 208–210); the AgentRunner chokepoint (tech-spec §2 Pillar 4 line 89; ADR-0004) is the only path by which a proposer can be invoked; the cheap monitor LLM (tech-spec §2 Pillar 5 lines 99–104; ADR-0005) gates every commit phase. The substrate question is closed. The orchestration question — *what triggers fire what passes against what edges in what order, and how does the result reach the user* — is open.

This ADR closes the orchestration question for six behaviors that together define how IntentGraph reacts when the spec changes, when the code drifts, when a requirement quietly ages out, when the user explicitly pivots, when a new spec is being authored, and when the AI itself proposes new substrate. Without an explicit commitment, each Phase 4 task that touches drift or authoring reacts to its own trigger in its own way: the markdown chokidar watch (tech-spec §6 phase 3 line 451) writes back without invoking propagation; the AST diff (tech-spec §6 phase 4 line 456) emits drift events without re-verifying obligations on descendants; intent edits made through the TipTap node editor (tech-spec §3.5 line 143) re-render but do not impact-check; new-node creation through any path lands without checking against the project's vision or sibling neighborhood. The cumulative effect is the failure mode the architecture was designed against: code is no longer a verifiable projection of intent because the projection's verification step does not run except at boundaries that nobody crosses, and the AI compounds the problem by authoring new substrate that contradicts what is already there.

The six behaviors below are commitments to the propagation pipeline (reactive: §1–§4) and the authoring gate (prospective: §5–§6). They do not change the substrate; they change which substrate operations the orchestrator runs in response to which event. Each behavior names the trigger, the orchestration steps in order, the inbox surfacing format and tier per ADR-0020 / ADR-0022, the monitor LLM interaction per ADR-0005 / ADR-0021, the confidence vocabulary interaction per ADR-0022 / ADR-0024, and the cost profile.

The decision is load-bearing for Phase 4 specifically because Phase 4 is where the AgentRunner, drift detection, and monitor LLM all land at once (tech-spec §6 phase 4 lines 455–464). If propagation orchestration is not committed before Phase 4 task decomposition, the inbox volume problem the synthesis names as structural (synthesis §Q2 finding 1, lines 108–110) becomes a *random* volume problem rather than a *managed* one — items appear because some path triggered them, not because the orchestration intentionally surfaced them.

## Decision

**Six orchestration behaviors are committed.** Four reactive (drift on intent edit, drift on code edit, stale-requirement detection, explicit scope-change escape hatch) and two prospective (conflict detection on new spec authoring, AI-initiated authoring conflict gate). The substrate is unchanged; the orchestrator's response to six classes of event is specified.

**Why one ADR and not two.** The reactive and prospective flows are tightly coupled in three load-bearing ways. (a) **Shared substrate:** both read the same edges (`realizes`, `depends_on`, `syncs_with`, `constrains`), the same `event_log`, the same `node.confidence` enum, the same `trace_event` shape, the same vec tables for PPR. Splitting them across ADRs would force one to depend on the other's substrate commitments, and the dependency direction is symmetric — neither is foundational to the other. (b) **Shared monitor verdict path:** §1 step 4, §5 step 4, and §6 step 2 all route a proposer's "is this consistent" judgment through the same monitor invocation pattern per ADR-0005 / ADR-0021. The cost envelope, the monitor-LLM language rules, the chevron-overlay rendering, and the cache key shape are all unified across the three; specifying them in separate ADRs would invite drift. (c) **Shared inbox surfacing patterns:** §1's grouped row, §5's commit-time modal, and §6's paired and bundled rows all consume the same Type 1/Type 2 design tokens from ADR-0020 and the same Tier 1/2/3 conventions from ADR-0022. The wire format extensions in `packages/shared/src/protocol/` are co-evolved across all six behaviors. Separating prospective into its own ADR would let the prospective flow drift in implementation — different tier conventions, different monitor framing, different cache invariants — exactly the failure mode this ADR's commitment-to-orchestration is designed to prevent. The breadth is the cost; the unification is the value.

### 1. Drift on intent edit (downstream impact pass)

**Trigger.** A write to `node.body` for any node of `kind ∈ {intent, constraint, decision, rationale}`. The trigger fires regardless of the write path: markdown sync via chokidar (tech-spec §6 phase 3 line 451), TipTap node editor (tech-spec §3.5 line 143), MCP `graph.upsert_node` (tech-spec §5.1 line 382), the resolver UI (ADR-0023). The single chokepoint — `node-write.ts` from ADR-0024's §Implementation implications — emits an `intent.changed` event after the OCC-versioned write commits.

**Orchestration steps.**

1. **Graph traversal.** From the changed node, traverse outward along `realizes`, `depends_on`, `syncs_with`, and `constrains` edges (tech-spec §4.2 lines 208–210). Edge direction is the natural one: `realizes` from code to intent so traversal walks *to* code; `depends_on` from dependent to dependency so traversal walks *to* dependents (the inverse direction is what we want — descendants of the changed node are nodes that depend on it); `syncs_with` is symmetric; `constrains` from constraint to intent so traversal walks *to* constrained intents. The traversal collects the descendant set bounded at depth 4 (configurable per project; the depth bound mitigates the fan-out concern from §Consequences below). PPR (tech-spec §3.7 lines 152–156) is **not** used for this pass — the impact pass is structural traversal, not relevance ranking; PPR's seeded-by-similarity shape is wrong for "which descendants are mechanically affected."
2. **Mark descendants.** For each descendant collected, apply a "parent changed" yellow drift indicator. Mechanically, this is a row in a per-event `drift_marker` projection table (application-layer; no DDL change — the marker is a `node`-shaped attribute set, computed from `event_log` traversal, materialized for query speed and torn down when the corresponding inbox group is closed). The yellow indicator is the Type 1 (drift detection) Layer-1 styling per ADR-0020 §3.
3. **Re-run verifiers.** For every obligation attached to the changed node and to each marked descendant (per ADR-0019's permissive attachment), invoke the verifier scheduler (ADR-0016). Obligations whose `kind ∈ {property, typecheck, example}` (tech-spec §4.3 lines 226–227) run inline if their `costClass ∈ {sub-ms, ms}` per ADR-0016 / tech-spec §3.4 line 134; obligations whose `costClass ∈ {s, minutes}` queue and post results asynchronously per tech-spec §3.4 line 138. The Coverage Verifier (Phase 2 task `p2-t07` per ADR-0016) is included because it bears on whether new descendants have lost their `realizes`/`verified_by` link.
4. **Run the proposer for semantic-inconsistency detection.** For each (changed-node, descendant) pair, the AgentRunner invokes a T1 proposer (Haiku 4.5 default per tech-spec §2 Pillar 4 line 92) with the new parent statement plus the descendant body. The proposer returns one of: `{consistent | possibly_inconsistent | proposal_to_update | proposal_to_delete}`. Each non-`consistent` verdict is a `proposed_patch` graph node per tech-spec §2 Pillar 3 line 79, with `confidence='inferred'` per ADR-0022 §1 (the proposer is inferring from two human-authored values; it has not asserted). Per ADR-0024 §3, accepting a proposer-generated patch never auto-promotes the descendant's confidence beyond `inferred`.
5. **Batch inbox surfacing.** All marked descendants and all proposer-generated proposals are tagged to a single change-event id (the `event_log.id` of the originating `intent.changed` event per tech-spec §4.6 line 274). The inbox shows them as a grouped item — one expanded row per change event, with descendants as nested rows. The user can accept, reject, or investigate per descendant; bulk-accept within Tier 3 is permitted per ADR-0022 §4. The grouped item is processable as a unit: a single "accept all" affordance applies to all descendants whose verifier outcomes are `pass` and whose proposer verdicts are `consistent` or `possibly_inconsistent` (the `proposal_to_update` and `proposal_to_delete` cases require per-descendant confirmation).

**Inbox surfacing format and tier (per ADR-0020 / ADR-0022).**

- Tier assignment depends on what the proposer and verifiers find:
  - Any verifier failure on the changed node or a descendant → the failed obligation goes to **Tier 1** (verifier failures are Tier 1 per ADR-0022 §2). The grouped impact-pass row stays at Tier 2 with the failure called out.
  - Any `proposal_to_delete` from the proposer → grouped row is **Tier 2** (high-leverage, since accepting the proposal deletes substrate).
  - Otherwise (consistent verdicts, optional `proposal_to_update`) → grouped row is **Tier 3** (low-priority backlog, filterable by default).
- Type per ADR-0020: the grouped row is **Type 1 (drift detection)** because the trigger is a graph mutation that causes downstream divergence. Individual proposer-generated proposals nested under the row are **Type 2 (proposal generation)**. The grouped row's keyboard binding is `V` (investigate, expand to show descendants); Y/N applies to nested proposal rows per ADR-0020 §3 Type 2.

**Monitor LLM interaction (per ADR-0005, ADR-0021).** Step 4's proposer is an AgentRunner action; per ADR-0005, every commit-phase action plus 5% sample plus all `safety_critical` mutations route through the monitor. The proposer's `proposal_to_update` and `proposal_to_delete` outputs are commit-phase actions because they propose substrate changes; both go through the monitor. Step 3's verifier outputs are not model calls and do not invoke the monitor. Step 1's traversal is not a model call. Step 5's inbox grouping is presentation, not a model call.

**Confidence vocabulary interaction (per ADR-0022, ADR-0024).** The changed node's confidence is governed by ADR-0024 §1 — preserved unless the user explicitly asserted. Descendants marked yellow inherit no confidence change from the marking; their confidence stays at whatever ADR-0024 dictates. Proposer-generated patches carry `inferred` confidence by construction (a model is the writer; the proposer's `declared_confidence` is `inferred` per ADR-0024 §1). Accepting a proposer patch does not promote the descendant — promotion requires the explicit assertion actions named in ADR-0024 §2.

**Cost profile.** Step 1 (traversal) is a graph query with depth-4 bound on a graphology in-memory traversal — sub-100ms even at 100k nodes (tech-spec §3.7 line 154 has the comparable PPR cost). No caching needed; it runs inline on every `intent.changed` event. Step 2 (marker materialization) is a small SQL write per descendant; inline, no caching. Step 3 (verifiers) is bounded by `costClass`; inline-eligible verifiers run synchronously, others queue. Step 4 (proposer) is the expensive one: one T1 model call per (changed-node, descendant) pair, one monitor verdict per non-`consistent` proposal. Cost scales linearly with descendant count. **Caching:** the proposer's input is `(changed_node.body_hash, descendant.body_hash)`; if both hashes match a prior `trace_event` row's input fingerprint, the prior verdict is reused. Cache hit rate depends on how often the same (parent, descendant) pair re-converges; in practice it is low for first-time impact passes and high on repeated reversions. Step 5 (inbox grouping) is presentation, no cost.

### 2. Drift on code edit (existing forward-sync flow, made explicit)

**Trigger.** `onDidSaveTextDocument` in the VS Code extension host (tech-spec §6 phase 4 line 456). The extension forwards the saved-file URI plus content hash to the skill via MCP.

**Orchestration steps.**

1. **Tree-sitter incremental reparse.** The extension owns the live CST per open file (tech-spec §3.2 line 116); the reparse runs in the extension host using `tree.edit` against the prior CST. The diff against the prior CST is computed at the AST grain via the 4-tier ladder (tech-spec §3.2 line 119): signature hash → body normalized hash → GumTree edit script → optional LLM behavior classifier. Steps 1–3 of the ladder are mechanical and cost-free; step 4 (LLM classifier) is invoked only when the prior tiers cannot disambiguate, which the synthesis-derived expectation is <10% of saves.
2. **Anchor resolution.** For each AST-grain change, the symbol-identity heuristic (tech-spec §3.2 line 118) re-binds the changed code to its prior `code_symbol` node by SCIP-first → composite-heuristic (signature 0.30 + body 0.35 + outgoing-call 0.20 + name 0.15) with thresholds 0.85 confident / 0.65 tentative → embedding tiebreaker at 0.65–0.85 → LSP rename events as hard overrides. Re-binding produces an updated `code_symbol` row (or a new one for orphaned symbols, per the `graph.diff_against_code` discriminator at tech-spec §5.1 line 386).
3. **Drift detection.** For each re-bound `code_symbol`, the orchestrator collects the intents that `realizes` it (tech-spec §4.2 line 209). For each (code_change, affected_intent) pair, the AgentRunner invokes a T0 proposer (Gemini Flash-Lite default per tech-spec §2 Pillar 4 line 91) with the code change plus the intent statement. The proposer returns one of: `{yes (still faithful) | no (drifted) | uncertain}`.
4. **Inbox surfacing.** Any verdict that is not `yes` produces a Type 1 (drift detection) inbox row per ADR-0020 §3. The row's Layer-1 keyboard binding is Y (accept drift, update intent) / N (reject drift, fix code) / V (investigate). The "accept drift, update intent" path interacts with confidence per ADR-0024 §2 — the assertion checkbox is unchecked by default; checking it promotes the intent to `asserted`, leaving it unchecked preserves prior confidence per ADR-0024 §1.

**Inbox surfacing format and tier (per ADR-0020 / ADR-0022).**

- `no (drifted)` verdicts on intents marked `safety_critical` → **Tier 1** (per ADR-0022 §2's "drift events flagged `safety_critical`" rule).
- `no (drifted)` verdicts on other intents → **Tier 2** (high-leverage; the user is choosing whether the code or the intent should change).
- `uncertain` verdicts → **Tier 3** (low-priority; the proposer's hedge is informational).
- Type per ADR-0020: **Type 1 (drift detection)**, yellow left-border, Y/N/V keyboard binding.

**Monitor LLM interaction.** Step 3's proposer is an AgentRunner action; the `no` verdict produces a commit-phase action when the user accepts (either accepting the drift updates intent substrate, or accepting the inverse path "fix code" produces a code mutation that itself goes through the regular forward-sync). Both routes route through the monitor per ADR-0005. The monitor's verdict surfaces per ADR-0021 — chevron-overlay on `require_human_review`, Tier 1 escalation on `block`, never modal except on `block`-override attempt.

**Confidence vocabulary interaction.** The code-edit trigger never directly modifies node confidence. The accept paths (Y or N) interact with confidence per ADR-0024 §2 — accepting the drift in the "update intent to match code" direction *with* the explicit assertion checkbox promotes to `asserted`; without, preserves prior confidence.

**Cost profile.** Step 1 (reparse + diff) is microseconds-to-milliseconds; inline. Step 2 (anchor resolution) is sub-millisecond per symbol on SCIP-cached lookups, milliseconds on composite-heuristic; inline. Step 3 (proposer) is a T0 model call per affected intent — Gemini Flash-Lite at $0.10/$0.40 per million tokens (tech-spec line 91). Per save, expected cost is well under $0.001 for typical 1–3 affected intents. **Caching:** input fingerprint is `(code_change_hash, intent.body_hash)`; cached as in §1's proposer cache. Cache hit rate is high on repeated saves of the same file with the same intent population. Step 4 (inbox surfacing) is presentation, no cost.

### 3. Stale requirement detection (background passes)

**Trigger.** Three distinct triggers, each a scheduled background pass with its own cadence:

- **3a — verifier-failure-on-previously-passing-constraint.** Triggered immediately when a verifier outcome flips from `verified` to `failed` on an obligation that has run successfully before (queryable from `obligation.last_run_at` per tech-spec §4.3 line 235 and the `event_log` history of `verifier:<id>` rows per tech-spec §4.6 line 277). This is event-driven, not scheduled; surfaces as soon as it fires.
- **3b — time-since-last-touched-on-intent-whose-anchored-code-has-changed-N-times.** A weekly Inngest scheduled function. Queries: for each intent, count `code_symbol` nodes that `realizes` it and whose `body_hash` has changed in the last 7 days (queryable from `event_log` rows where `kind` indicates a code mutation, joined to the `code_symbol` rows). For each intent where the count exceeds N (default N=5, configurable per project in `.intentgraph/config.json`), check whether the intent itself has been written to in the same window. If the intent has not been written to but its anchored code has churned more than N times, the intent is a stale-requirement candidate.
- **3c — cross-cutting-constraint-violation-spread.** A monthly Inngest scheduled function. For each constraint, run PPR (tech-spec §3.7 lines 152–156) seeded by the constraint node, then count how many distinct concept nodes in the top-K contain at least one obligation that has failed in the last 30 days. If the count exceeds M (default M=3, configurable per project), the constraint is a candidate for being itself outdated — failures are spreading across concept boundaries, which suggests the constraint is no longer the right narrowing.

**Orchestration steps (per trigger).**

- **3a:** No traversal. The flipped obligation's failure surfaces as a Type 5 (verifier outcome) inbox row per ADR-0020 §3 Type 5 — red left-border, headline "verifier failure on the affected symbol," subhead the counterexample summary. Tier 1 per ADR-0022 §2 (verifier failures are Tier 1).
- **3b:** The weekly job emits one digest item per stale-requirement candidate. The digest item is a Type 1 (drift detection) row variant — the substrate event is "intent's anchored code has churned without the intent being touched," which is a drift between the intent's currency and its referent. The row's Layer-1 headline names the intent and the churn count; Layer-2 shows the changed code symbols with their churn timestamps and the intent's `updated_at`; Layer-3 offers "review the intent" (opens detail panel) and "kick off a regeneration pass" (emits an `intent.changed` event manually, which fires §1's pipeline). Tier 3 per ADR-0022 §2 (low-priority, filterable; the slow-changing nature of the signal is what makes weekly the right cadence).
- **3c:** The monthly job emits one digest item per outdated-constraint candidate. The item is a Type 1 row variant — the substrate event is "constraint is failing across concept boundaries," which is drift between the constraint's narrowing and the concepts it claims to constrain. Layer-1 headline names the constraint and the concept-spread count; Layer-2 shows the affected concepts and their failed obligations; Layer-3 offers "review the constraint" and "demote constraint to draft" (an out-of-band action that requires a typed reason per ADR-0022 §4). Tier 3 per ADR-0022 §2 (the monthly cadence and the cross-concept signal are inherently low-urgency).

**Inbox surfacing format and tier (per ADR-0020 / ADR-0022).** Summarized in the per-trigger steps above. The 3b and 3c items are aggregated into a weekly/monthly **digest** view in the inbox sidebar, separated from the live inbox by a section divider. The digest section has its own status-bar count; it does not contribute to the per-day inbox-volume budget per ADR-0022 §2 / synthesis §Q2 finding 1 (lines 108–110).

**Monitor LLM interaction.** None of the three stale-detection triggers invoke the proposer. They are pure substrate queries (3a is a verifier-outcome flip; 3b is a churn-vs-touch comparison; 3c is a PPR query). They do not produce model calls and do not route through the monitor. If the user opens the Layer-3 "kick off a regeneration pass" affordance on a 3b digest item, that action emits an `intent.changed` event which then fires §1's pipeline including the monitor; the digest item itself is monitor-free.

**Confidence vocabulary interaction.** None. The digest items do not propose substrate changes; they surface candidates for human attention. Confidence is unchanged.

**Cost profile.**

- **3a** is event-driven and bounded by verifier flip rate; expected sub-1Hz on a typical project. No caching needed.
- **3b** is a weekly query over `event_log` filtered by date range and joined to `code_symbol` rows. SQL-only, no model calls. Expected cost is one `event_log` index scan per week; sub-second on a project-sized graph.
- **3c** is a monthly PPR pass per constraint. Per tech-spec §3.7 line 154, PPR is ~10 iterations × ~10ms per iteration on a 100k-node graph. With ~1000 constraints in a typical project, monthly cost is ~100 seconds of skill-side compute, run as a low-priority Inngest job. **Caching:** per-constraint PPR results cached with a 30-day TTL keyed by `(constraint_id, last_failure_count_hash)`; re-run when the failure count under the constraint changes. Cache hit rate is high — most constraints' failure populations are stable month-over-month.

### 4. Explicit scope-change escape hatch

**Trigger.** Explicit user action: a UI affordance ("declare scope change," keyboard shortcut TBD in Phase 4 task work) that opens a dialog requiring (a) the affected node id (or set of node ids), (b) a typed reason for the pivot per ADR-0022 §4, (c) optionally a window override (default 7 days, configurable per scope-change event up to 30 days).

**Orchestration steps.**

1. **Commit the change.** The change is committed via the same `node-write.ts` chokepoint as ADR-0024 §Implementation. The accompanying `event_log` row carries `kind='scope.changed'` with payload `{node_id, reason, window_days, suppressed_event_ids: []}`. The user's reason is preserved in the `event_log.payload` column per tech-spec §4.6 line 281. Per ADR-0024 §2, the scope-change action **does** count as explicit assertion (the user is committing to a deliberate pivot); the affected node's confidence promotes to `asserted` if it was below.
2. **Run the impact pass.** §1's traversal (steps 1 and 2) runs identically — descendants are collected and yellow-marked. The user sees blast radius. This is the load-bearing point: scope-change suppresses *reconciliation proposals*, not *visibility*. Users who declare scope change still see what their pivot affects.
3. **Run the verifiers.** §1 step 3 runs identically. Verifier outcomes are not suppressed because verifier outcomes are not opinions; they are objective claims about whether code conforms to constraint, and a deliberate pivot does not change whether the code typechecks.
4. **Suppress the proposer.** §1 step 4 is **skipped** for the duration of the configured window for any descendant in the impact set. Concretely: the orchestrator records the `event_log.id` of the `scope.changed` event in a `scope_change_active` projection (application-layer; queried at proposer-invocation time). Before invoking the proposer for a (changed-node, descendant) pair, the orchestrator checks whether the descendant is in any active scope-change suppression set; if so, the proposer is skipped and a placeholder "scope change in progress" inbox row is emitted at Tier 3 instead of the usual proposer-generated rows.
5. **Create a decision node.** A new `node` row of `kind='decision'` (tech-spec §4.1 line 192) is created with body `{context: <user's typed reason>, alternatives: [], chosen: <change summary>, consequences: <window and affected node count>}`. The decision node is linked to the changed node via a `decides` edge (tech-spec §4.2 line 209) and to the originating `event_log.id` via the `event_log.task_id` reference (tech-spec §4.6 line 278). The decision node's confidence is `asserted` per ADR-0024 §2 (the user authored it from scratch via the dialog).
6. **Window expiry.** When the window expires (the Inngest scheduled function checks daily), the suppression set entry is removed. From the next save or next intent edit forward, §1's pipeline runs normally on descendants previously suppressed. The `event_log` rows produced during the suppression window are not retroactively run through the proposer — the suppression is honest: those events were intentionally not analyzed, and that is recoverable from the `event_log` chain.

**Inbox surfacing format and tier (per ADR-0020 / ADR-0022).**

- The scope-change dialog produces no inbox row of its own — the action is acknowledged via the dialog's confirmation, not via an inbox queue.
- The §1 step 2 markings still surface as the Type 1 grouped row, but its expanded view shows "scope change in progress (X days remaining)" instead of proposer-generated descendants. Tier 3 per ADR-0022 §2 (the visibility is informational; the user has already declared the pivot).
- After window expiry, the next save or intent edit on a previously-suppressed descendant fires §1 normally and produces the usual Type 1/Type 2 rows at their natural tier.
- The decision node from step 5 surfaces in the canvas via the existing decision-node rendering (Phase 4 task per tech-spec §3.5); it does not generate an inbox row.

**Monitor LLM interaction.** The scope-change action itself is a graph mutation that creates a decision node and changes a node's body; per ADR-0005, the mutation is a commit-phase action and goes through the monitor. The monitor's verdict on a scope change is informational (the user has declared the pivot deliberately; an `allow` verdict is the expected case, a `require_human_review` chevron may surface, a `block` verdict is rare and would require the override flow per ADR-0021 §2). Critically, the monitor does **not** evaluate suppressed proposals during the window — there are no proposals during the window because the proposer is skipped.

**Confidence vocabulary interaction.** Per step 1 above, the scope-changed node's confidence promotes to `asserted` because the user explicitly asserted via the dialog. The decision node from step 5 is `asserted` per ADR-0024 §2 (authored from scratch). Descendants in the suppression set retain whatever confidence they had; they are neither promoted nor demoted by the scope-change event, consistent with ADR-0024 §1 (confidence transitions only on writes to *that* node, not on writes to a parent).

**Cost profile.** Step 1 (commit) is a single SQL write plus an `event_log` row; sub-millisecond. Step 2 (traversal) is identical to §1 step 1 — sub-100ms. Step 3 (verifiers) is bounded as in §1. Step 4 (suppression check) is an indexed lookup against `scope_change_active`; sub-millisecond per descendant. Step 5 (decision-node creation) is a single SQL write. Step 6 (expiry) is a daily cron pass over the suppression projection; sub-second. The escape hatch's cost is dominated by the verifier passes from step 3, which would have run anyway under §1; the *savings* are step 4 of §1 (the proposer per descendant pair plus the monitor verdict per non-`consistent` output), which is the costly step that the escape hatch suppresses.

### 5. Prospective conflict detection on new spec authoring

**Trigger.** A proposed write that would create a *new* `node` row of `kind ∈ {intent, constraint, decision, rationale}`. The trigger fires before the OCC-versioned commit lands — concretely, the same `node-write.ts` chokepoint from ADR-0024's §Implementation intercepts the write, recognizes the absence of a prior row at that id, and routes through the prospective-check pipeline before allowing the commit. The trigger fires identically whether the writer is the user (via the markdown-sync chokidar path per tech-spec §6 phase 3 line 451, the TipTap "create new node" affordance per tech-spec §3.5 line 143, or MCP `graph.upsert_node` per tech-spec §5.1 line 382) or the AI (any AgentRunner-routed creation; §6 below specifies the AI-side gate that runs *before* the AI's proposal even reaches this trigger).

The reason the trigger is creation-only and not also edit-of-existing: edits of existing nodes go through §1's reactive impact pass, which already covers the "this change conflicts with descendants" case. The prospective trigger is specifically for *new* substrate landing in a graph that has its own existing constitution. A future ADR may extend the trigger to material edits (rewrites that effectively author a new claim under an existing id); for v1, the boundary is creation versus modification.

**Orchestration steps.**

1. **Vision check.** The orchestrator collects the project's top-level intents and the architectural-pillar set (the latter materialized from the accepted ADRs in `docs/adr/` plus the five pillars enumerated at tech-spec §2 lines 64–104). The collection is cached at the skill side with TTL 1 hour and invalidated on any write to a top-level intent or any new ADR commit; the cache key is `(top_level_intent_count, last_adr_commit_hash)`. The proposed-node body plus the collected vision is passed to a T1 proposer (Haiku 4.5 default per tech-spec §2 Pillar 4 line 92) with a vision-contradiction prompt. The proposer returns one of: `{aligned | possibly_contradicts | clearly_contradicts}` per top-level intent and per pillar, plus an aggregate verdict.
2. **Sibling check.** The orchestrator collects adjacent nodes to the proposed node's intended position: `parent_id` chain (tech-spec §4.1 line 179), `parent_id`-siblings (other nodes sharing the same `parent_id`), and nodes connected to the proposed node's referenced ids by `syncs_with` or `constrains` edges (tech-spec §4.2 lines 208–210). For nodes the proposed node references in its body (e.g., a constraint that names the intent it constrains), the orchestrator also collects the referenced intent's `realizes`-connected siblings — the local neighborhood of the referent. The proposed-node body plus the adjacent-node bodies is passed to a T1 proposer with a sibling-contradiction prompt. Output is one of: `{consistent | possibly_inconsistent | clearly_contradicts}` per adjacent node, plus an aggregate verdict.
3. **Supersession check.** The orchestrator runs PPR (tech-spec §3.7 lines 152–156) seeded by the proposed-node embedding (computed inline against the vec table per tech-spec §4.10 lines 359–369), top-K=20. For each PPR-returned existing node whose similarity exceeds 0.85 (a high-similarity threshold; the goal is to catch claims that the proposed node is functionally restating, not loosely related material), the orchestrator passes the proposed-node body plus the candidate body to a T1 proposer with a supersession prompt. Output is one of: `{independent | overlaps_partially | likely_supersedes}` per candidate. Candidates marked `likely_supersedes` are surfaced as supersession candidates in step 5.
4. **Monitor verdict on the conflict-detection results.** The aggregate of steps 1–3 is itself an AgentRunner action — the proposer's "is this a conflict" judgment is exactly the kind of plausible-but-possibly-wrong claim the cheap monitor is good at auditing per ADR-0005 and Baker et al. (tech-spec §2 Pillar 5 lines 99–104). The monitor receives the aggregate verdict plus the proposer's evidence per step (the cited vision intents, the cited adjacent nodes, the cited supersession candidates) and returns its standard `{flagged, score, categories[], evidence, recommended_action}` shape per tech-spec §4.7 line 309. Critically, the monitor here audits the *proposer's conflict claims*, not the proposed node's content — the monitor's role is to catch the proposer falsely claiming a conflict (false positive that would block legitimate spec authoring) or falsely clearing a conflict (false negative that would let a contradicting node through). The monitor verdict is recorded on the same `trace_event` row as the conflict-detection proposer call per tech-spec §3.8 line 160.
5. **Outcome routing.** The aggregate of steps 1–4 produces one of three outcomes:
   - **No conflicts.** Steps 1, 2, 3 all return aligned/consistent/independent aggregates; the monitor verdict is `allow`. The proposed node commits with no friction. The trigger pipeline returns control to the original write path, which proceeds with the OCC-versioned commit. A `trace_event` row records the prospective-check outcome for audit.
   - **Conflicts detected.** Any of steps 1, 2, or 3 returns a `clearly_contradicts` aggregate, OR the monitor's verdict is `require_human_review` or `block`. The commit is **paused**; the user (in the user-trigger case) sees a blocking modal at commit time titled "Potential conflict" with the conflicting nodes rendered side-by-side per ADR-0023's resolver-style "Yours" / "Theirs" framing (the conflicting node is "Theirs," the proposed node is "Yours"). Three options per ADR-0024's structured-affordance pattern: **(a) Revise the new spec** — the user returns to the editor with the proposed body still present; no commit happens. **(b) Archive the conflicting nodes** — the conflicting nodes are soft-deleted (set `node.deleted_at` per tech-spec §4.1 line 184), the archival is recorded in `event_log` as `kind='node.archived_for_conflict'` with the proposed-node id and the conflict evidence in payload, and the proposed node then commits. **(c) Commit anyway with a typed reason** — the user types a reason per ADR-0022 §4's structured-override-reason rule; a new `node` of `kind='decision'` is created with body `{context: <user's reason>, alternatives: [<conflicting-node titles>], chosen: <proposed-node title>, consequences: 'committed against detected conflict'}` and `confidence='asserted'` per ADR-0024 §2 (the user authored from scratch); a `decides` edge links the decision to the proposed node and a `references` edge links it to each conflicting node; the proposed node then commits.
   - **Likely-stale detection.** Step 3 returns `likely_supersedes` candidates and steps 1, 2 are clear of contradictions; the monitor verdict is `allow` or `require_human_review`. The commit is **paused** with a lower-severity dialog titled "Possible supersession" listing the candidate-superseded nodes. Two options: **(a) Yes, this supersedes them** — the candidates are archived with `event_log.kind='node.superseded'` linking to the proposed node id, the proposed node commits, and a `supersedes` edge (tech-spec §4.2 line 209) is added from the proposed node to each archived candidate. **(b) No, they coexist** — the proposed node commits without archival; a `trace_event` records the user's "no" response to suppress re-detection on this exact pair for 30 days (the suppression is keyed by `(proposed_node_id, candidate_node_id)`).

**Inbox surfacing format and tier (per ADR-0020 / ADR-0022).**

- The "no conflicts" outcome surfaces no inbox row — the commit happens silently as the user expected.
- The "conflicts detected" outcome surfaces the conflict modal at commit time, **not** as an inbox row. This is the user's own pending action, not a queue item; routing it through the inbox would force the user to leave the editing flow they were in, which the synthesis's §Q2 context-switching analysis (line 102, "each context switch costs 20+ minutes of recovery and ~20% of cognitive capacity") names as a cost to avoid. After the user resolves the modal via option (a), (b), or (c), no inbox row is generated — the resolution is the terminal action.
- The "likely-stale detection" outcome similarly surfaces at commit time, not via the inbox. The lower-severity dialog reflects the synthesis's "modal/interruptive treatment is reserved for the rarest and most consequential alert tier" rule (ADR-0021 §3): supersession is medium-stakes (the user's "no" is always available and cheap), so the dialog is non-blocking-after-acknowledgment — the user can dismiss without choosing and the proposed node commits with a flag in the `event_log` that supersession was detected but unanswered, surfacing later as a Tier 3 digest item per §3.
- Type per ADR-0020: when a supersession-detected commit lands without resolution and surfaces later, the digest item is **Type 1 (drift detection)** because the substrate event is "two nodes coexist where the proposed node likely supersedes an existing one" — a kind of structural drift between authored substrate and effective substrate. Layer-1 styling per ADR-0020 §3 Type 1 (yellow border).

**Monitor LLM interaction (per ADR-0005, ADR-0021).** Step 4 above is the load-bearing monitor interaction: the monitor audits the proposer's conflict-detection output, not the proposed-node content. This is the right framing because step 4's question — "is the proposer correctly identifying conflicts" — is exactly the structured-judgment-on-AI-output role Baker et al. show the cheap monitor handles well (tech-spec §2 Pillar 5 lines 99–104). The monitor's `block` verdict on a step-4 audit means the monitor disagrees strongly with the proposer's conflict claim; in that case, the conflict modal still surfaces but with a chevron-overlay per ADR-0021 §1 indicating "the monitor questioned the conflict detection" so the user can weight the proposer's evidence accordingly. A `block` verdict on the monitor side never *creates* a conflict that the proposer did not find — the monitor is only allowed to question, not to invent — so a step-4 `block` against a no-conflict aggregate routes to the normal "no conflicts" outcome with a `trace_event` row recording the monitor's disagreement for later precision review per tech-spec §7-D.

**Confidence vocabulary interaction (per ADR-0022, ADR-0024).** The proposed-node confidence at commit time is `write.declared_confidence` per ADR-0024 §1 — for user-authored new nodes via the dialog, that is `asserted` per ADR-0024 §2; for AI-authored new nodes (the §6 case), that is `inferred`. The conflict-detection pipeline does **not** modify the confidence — it routes around the confidence question entirely, since "is there a conflict" and "how confident is the author" are orthogonal axes. The decision node created in option (c) is `asserted` per ADR-0024 §2 (authored from scratch). Archived nodes via option (b) or the supersession path retain their prior confidence in the soft-deleted state; if a future user un-archives, the prior confidence is what they see.

**Cost profile.** Step 1's vision collection is a graph query with a 1-hour cache; cache hit is sub-millisecond, cache miss is a few hundred milliseconds for the top-level-intent + ADR collection. The proposer call in step 1 is one T1 model call against a prompt of size O(top_level_intent_count + adr_count). For a project with ~20 top-level intents and ~25 ADRs, prompt size is well within Haiku 4.5's context, and latency is ~400–800ms. Step 2's adjacent-node collection is a graph-traversal query with edge-walk; sub-100ms. The proposer call in step 2 is one T1 model call with prompt size O(adjacent_node_count); for a typical neighborhood of 5–15 nodes, latency is ~300–600ms. Step 3's PPR pass is ~100ms per tech-spec §3.7 line 154; the per-candidate proposer calls are bounded at K=20 candidates filtered by the 0.85 similarity threshold (which typically returns 0–3 candidates), so the proposer-call cost is one T1 call per surviving candidate at ~200–400ms each. Step 4's monitor call is one Llama 3.3 70B on Groq invocation per ADR-0005's default; latency 1–3s per tech-spec §3.8 line 160. **Total prospective-check latency: ~500ms–2s typical, up to ~3–4s when all three steps return candidates that need proposer evaluation.** This is the user-perceived commit latency that did not exist before.

**Caching.** Step 1's vision collection is cached at the skill side with the key named above; per-prompt proposer outputs are cached with key `(proposed_node_body_hash, vision_collection_hash)` — re-running the same prospective check on the same proposed body returns the cached verdict. Step 2's adjacent-node collection is per-write, no cache needed (the neighborhood is small). Step 2's proposer outputs are cached with key `(proposed_node_body_hash, adjacent_node_id_set_hash)`. Step 3's PPR is cached per tech-spec §3.7 / ADR-0005's existing retrieval cache; the per-candidate proposer outputs are cached with key `(proposed_node_body_hash, candidate_body_hash)` — this cache is shared with §1 step 4's proposer cache (the underlying question "do these two specs agree" is the same). Step 4's monitor verdict is cached with key `(aggregate_verdict_hash, proposer_evidence_hash)` so re-running an identical conflict-detection produces an identical monitor verdict without a fresh model call. Cache hit rates are expected to be moderate-to-high once a project has been worked on for a few days, because authors often try variations of the same proposed body.

### 6. AI-initiated spec authoring conflict gate

**Trigger.** Any AgentRunner-routed action that would *propose* a new `node` row of `kind ∈ {intent, constraint, decision, rationale}`. Sources include: forward-sync code-generation that produces a new intent (tech-spec §6 phase 3 line 79; tech-spec §6 phase 4 line 458 names `intent.extract` among the first agent functions), drift reconciliation that proposes a new constraint to narrow a divergent intent (§1 step 4 of this ADR), `intent.extract` proposals from the intent-extractor subagent (CLAUDE.md "Subagents" section), proposer-generated supersession suggestions, or any future agent-initiated authoring path. The gate fires *inside AgentRunner*, before the proposal is materialized as a `proposed_patch` graph node per tech-spec §2 Pillar 3 line 79 — i.e., before the user can see the proposal in any inbox.

The reason the gate runs inside AgentRunner: per ADR-0004, AgentRunner is the single chokepoint to model providers, so it is the only place where every model-generated node-creation proposal is structurally guaranteed to pass through. Routing the gate anywhere else (e.g., at inbox materialization) would let proposals from any future AI path bypass it.

**Orchestration steps.**

1. **Run the §5 three checks on the AI's proposed output.** The AI's drafted node body is fed through the same vision check, sibling check, and supersession check from §5 steps 1–3. The proposer used for the checks is **a different AgentRunner invocation** from the one that produced the proposal — the same model is acceptable (T1 Haiku 4.5), but the call is fresh, with a fresh prompt that asks "does this proposed node conflict with the existing graph" rather than "produce a node." This separation matters: it means the conflict-detection proposer is not biased by having just produced the proposal. Both invocations are recorded as separate `trace_event` rows per tech-spec §4.7 lines 289–323, with the second row's `parent_trace_id` (line 292) pointing to the first so the audit chain is reconstructable.
2. **Run the §5 step 4 monitor verdict on the conflict-detection output.** Identical to §5 step 4. The monitor audits the conflict-detection proposer's claims.
3. **Outcome routing inside AgentRunner.**
   - **Vision-contradicting proposal** (step 1's vision check returned `clearly_contradicts` aggregate, monitor concurs at `allow` or `require_human_review`). The proposal is **rejected before reaching the inbox.** The rejection is recorded in the trace store: a `trace_event` row with `kind='mutation'`, `produced_mutations='[]'` (the rejection means no mutation was produced), and a structured `verifier_outcomes` field carrying the conflict evidence. A separate `event_log` row is written with `kind='agent.proposal_rejected_pre_inbox'` and payload including the proposed-node body, the conflicting vision intents, and the proposer's evidence. The `monitor_verdict` on the trace row carries the monitor's verdict on the conflict detection. The user never sees this proposal; the rejection is fully auditable for later review per tech-spec §7-D ("maintain a labeled set of 200+ historical commits"). If the monitor `block`-verdicts the conflict-detection output (i.e., the monitor disagrees strongly with the proposer's claim that there is a vision contradiction), the proposal escapes the rejection and routes to the normal inbox surfacing path with a chevron-overlay indicating "the monitor questioned the conflict gate" per ADR-0021 §1; the user gets to see the proposal and decide.
   - **Sibling-contradicting proposal** (step 1's sibling check returned `clearly_contradicts` aggregate against one or more adjacent nodes). The proposal is **surfaced as a paired inbox item** with explicit "this conflicts with X" framing. Mechanically: the proposed node is materialized as a `proposed_patch` per tech-spec §2 Pillar 3 line 79; the conflicting adjacent nodes are referenced by id; the inbox row is rendered as a Type 2 (proposal generation) row per ADR-0020 §3 with a Layer-1 headline that reads "AI proposed X, which conflicts with Y" and Layer-2 expansion showing the proposed node and each conflicting node side-by-side per ADR-0023's resolver-style framing. The keyboard binding is **Y/N/V** with semantics "Y: keep the AI's proposed X (archives Y after typed reason); N: reject the AI's proposal (Y stays); V: investigate (open the resolver-style side-by-side view)." This framing makes the conflict legible at the inbox row rather than after the user accepts.
   - **Supersession-implying proposal** (step 1's supersession check returned `likely_supersedes` candidates). The proposal is **bundled with the supersession decision** as a single inbox item. Mechanically: the proposed `proposed_patch` carries a `bundled_supersession_candidates` list of node ids in its body. The inbox row is rendered as a Type 2 row with a Layer-1 headline that reads "AI proposed X, which supersedes Y (and Z, and …)" and Layer-2 expansion showing the proposed node, each candidate-superseded node, and a single combined Y/N affordance — accepting the row commits the proposed node *and* archives the candidates as one operation, with a `supersedes` edge added from proposed to each candidate. The user resolves the proposal and the supersessions in one decision rather than as N separate decisions, respecting the synthesis's volume-management discipline (ADR-0022 §2 / synthesis §Q2 finding 1 lines 108–110).
   - **No-conflict proposal** (all checks clear, monitor `allow`). The proposal is materialized as a normal `proposed_patch` and surfaces in the inbox per the existing Type 2 flow per ADR-0020 §3 — no special framing.

**Inbox surfacing format and tier (per ADR-0020 / ADR-0022).** The vision-contradicting case produces no inbox row by design — the row would be the failure mode the synthesis warns against ("plausible AI fabrications that fill gaps," synthesis §"Mental-Model Gap" lines 547–555). The sibling-contradicting case surfaces at **Tier 2** (high-leverage; the user is choosing between two articulated positions). The supersession-bundled case surfaces at **Tier 2** if the candidates being superseded include any `asserted`-confidence nodes (the user is being asked to retire material they previously committed to) or **Tier 3** otherwise. The no-conflict case surfaces at whatever tier the underlying proposal would have warranted before the gate — the gate does not change tier for clean proposals.

**Monitor LLM interaction (per ADR-0005, ADR-0021).** The gate's step 2 routes the conflict-detection output through the monitor. This is the key load-bearing monitor interaction for §6: the monitor's role is to prevent the gate from being a silent suppression mechanism. If the proposer falsely claims a vision conflict on a clean proposal, the proposal would be rejected pre-inbox without the user ever knowing; the monitor's audit catches that failure mode by flagging when the conflict-detection evidence does not support the conflict claim. Per ADR-0021 §1 language rules, the monitor here is auditing the *gate's proposer*, not the user — language rules are inherited unchanged. The monitor's verdict is preserved on the `trace_event` row alongside the gate decision so the QA pass per ADR-0013/0014 can grep for `agent.proposal_rejected_pre_inbox` events whose monitor verdicts dispute the rejection.

**Confidence vocabulary interaction (per ADR-0022, ADR-0024).** The AI's proposed node carries `confidence='inferred'` per ADR-0024 §1 (the AI is the writer; `declared_confidence='inferred'`). The gate does not modify confidence. The supersession-bundled case archives candidates regardless of their confidence (an `asserted` node can be archived if the user accepts the bundled proposal — this is the only path where AI-initiated authoring can effectively retire `asserted` substrate, and it requires explicit user acceptance via the bundled Y affordance, which is the same friction shape as ADR-0024's "demote confidence" path).

**Cost profile.** The §6 gate runs the §5 checks plus a §5 step 4 monitor verdict on every AI-initiated authoring action. The cost per AI proposal is therefore **the §5 cost added to the cost of producing the proposal** — concretely, one or two T1 model calls (gate's conflict-detection proposer plus zero, one, or several proposer calls per surviving candidate per §5 step 3) plus one monitor call. Latency budget is the same as §5: ~500ms–2s typical. **The cost is non-trivial relative to the proposal-generation cost itself**, because the proposal is often a single T0 or T1 call (generating prose) and the gate adds a second-order overhead. For high-volume agent-initiated paths (e.g., `intent.extract` running over a fresh codebase that produces dozens of intents in a batch), the gate cost stacks linearly. Mitigations:

- The proposer caches from §5 are shared with §6, so identical proposals against an unchanged graph hit the cache.
- For batch authoring paths, the gate runs in parallel across proposals up to the AgentRunner concurrency limit (Inngest's `concurrency: { key: "event.data.intentNodeId", limit: 1 }` per node from tech-spec §3.3 line 125 plus a configurable parallel-gates limit at the agent-runner level).
- The vision collection cache (§5) is workspace-scoped and invalidated only on top-level-intent or ADR changes, so the vision-check cost amortizes across all proposals in a session.

**Caching.** Identical to §5's caching, with the additional note that the gate's conflict-detection-proposer cache is keyed by `(proposed_node_body_hash, vision_collection_hash, adjacent_node_id_set_hash, supersession_candidate_set_hash)` so the same proposed body against the same graph state always returns the same cached verdict regardless of whether the trigger came from §5 or §6.

## Schema implications

**No baseline-migration DDL change.** All six behaviors read existing columns:

- `event_log` (tech-spec §4.6 lines 273–286) is the canonical record for every trigger and every commit; new application-layer `kind` values (`intent.changed`, `scope.changed`, plus the existing mutation kinds) require no migration per the existing free-form `kind TEXT NOT NULL`.
- `node.confidence` (tech-spec §4.1 lines 177–178) drives the §1 step 4 proposer's `declared_confidence` and the §4 step 1 promotion.
- `obligation.last_run_at` (tech-spec §4.3 line 235) drives the §3a verifier-flip detection.
- `edge.kind` (tech-spec §4.2 lines 208–210) drives the §1 step 1 traversal.
- `trace_event` (tech-spec §4.7 lines 289–323) records every proposer call and every monitor verdict per the existing AgentRunner-only chokepoint (ADR-0005).
- The vec tables (tech-spec §4.10 lines 359–369) drive the §3c PPR seeds.

Three application-layer projection tables are introduced. They are **not** baseline-migration DDL — they are recoverable derivations from `event_log`, owned by the orchestrator's projection-maintenance modules (see Implementation implications), and created lazily on first use rather than declared in the schema layer. Drop-and-rebuild is always safe; dropping any of them costs at most an `event_log` rescan, not data loss:

- `drift_marker(event_id, descendant_node_id, marked_at, cleared_at?)` — materializes the §1 step 2 yellow markings for fast inbox query. Torn down when the corresponding inbox group is closed.
- `scope_change_active(event_id, node_id, window_expires_at)` — materializes the §4 step 4 suppression set for fast lookup at proposer-invocation time. Torn down at window expiry.
- `supersession_suppression(proposed_node_id, candidate_node_id, suppress_until)` — materializes the §5 outcome (b) "no, they coexist" suppression for re-detection avoidance over the 30-day window.

All three projection tables live in the per-branch DB (per ADR-0023) and are recoverable from `event_log` replay if dropped. Phase 4 implementation owns the create-on-first-use logic; the baseline Drizzle schema (ADR-0015) is unchanged.

The wire format from skill to webview adds five envelope shapes, all in `packages/shared/src/protocol/` (TypeScript-only, no schema impact):

- `inbox.grouped_event` — §1 change-event id and nested descendant rows.
- `inbox.paired_conflict` — §6 sibling-contradicting paired-row payload (proposed node + conflicting adjacent node).
- `inbox.bundled_supersession` — §6 supersession-bundled row payload (proposed node + candidate-superseded list).
- `commit.conflict_modal` — §5 conflict-detected payload (proposed node body, conflicting nodes, option set).
- `commit.supersession_dialog` — §5 likely-stale payload (proposed node body, supersession candidates, two-option set).

`event_log` gains application-layer convention values: `node.archived_for_conflict`, `node.superseded`, `agent.proposal_rejected_pre_inbox`. All are accommodated by the existing free-form `kind TEXT NOT NULL` per tech-spec §4.6 line 277.

## Consequences

What this enables:

- **The four-pillar substrate becomes a coherent propagation pipeline.** Drift detection, the AgentRunner chokepoint, the verifier scheduler, the monitor LLM, and PPR retrieval are all already committed; this ADR is the orchestration that wires them into the user-facing behavior the dogfooding ladder L2 requires (CLAUDE.md L2 gate: ≥80% of symbol-vs-intent drift auto-detected, ≥50% of suggestions accepted as-is).
- **Stale requirements become detectable without becoming intrusive.** The three §3 triggers respect the synthesis's structural-volume finding (§Q2 finding 1, lines 108–110, "the inbox volume problem is structural, not a tuning issue") by routing slow-changing signals through a digest channel that does not consume the per-day budget. The user can ignore the digest indefinitely; the substrate keeps the candidates surface-able when the user is ready.
- **Intentional pivots are first-class.** The §4 escape hatch resolves the "AI second-guessing on a deliberate pivot is annoying" failure mode by removing the proposer from the loop while preserving visibility. The decision node from §4 step 5 becomes the audit-traceable record of the pivot — future contributors can grep `decision` nodes for the pivot's reason.
- **The inbox grouping respects cognitive-load research.** The synthesis (§Q2 design implications, lines 122–127) recommends a three-tier sort with explicit visual tier markers; this ADR's grouped impact-pass row is consistent with that — a single Tier-2 grouped row plus nested descendants is one *decision* for the user, not N decisions, even when fan-out is large. This is the load-bearing reason the impact pass batches rather than per-descendant streams.
- **Monitor cost is bounded.** Steps 1, 2, 3 of §1 produce no model calls; only step 4's proposer goes through the monitor. The escape hatch in §4 suppresses step 4 explicitly. The §3 stale-detection passes produce no model calls at all. Monitor cost scales with proposer call volume, which scales with intent-edit frequency on nodes with many descendants — bounded and predictable.

What this costs:

- **The propagation pipeline is non-trivial work for Phase 4.** Estimate: §1's `impact-pass.ts` is ~300–400 lines including traversal, marker maintenance, verifier invocation, and proposer routing. §2's `forward-sync.ts` is ~200 lines (the trickiest part is anchor resolution, which already lives in tree-sitter / SCIP utilities). §3's `stale-detection.ts` is ~250 lines including the three scheduled functions and the digest projection. §4's `scope-change.ts` is ~200 lines including the suppression projection and the window-expiry cron. §5's `prospective-check.ts` is ~300–400 lines including the three checks, the cache layer, and the outcome routing. §6's `authoring-gate.ts` is ~200 lines (it composes §5's checks; most of its weight is in routing). Total: roughly 1450–1650 lines of new orchestration code, plus the webview surfaces (~700 lines for GroupedEventRow, DigestSection, ScopeChangeDialog, ConflictModal, SupersessionDialog, PairedConflictRow, BundledSupersessionRow) and the wire-format extensions (~250 lines for the five envelope shapes). At Phase 4's eng-week budget (12 eng-weeks per tech-spec §6 phase 4 line 499), this is roughly 3–4 eng-weeks — material but proportionate to the value the prospective and reactive flows together deliver.
- **Automatic propagation can produce large inbox volume on top-level intent edits.** A single edit to a concept-root intent might fan out to dozens of descendants. The synthesis's §Q2 finding 1 (lines 108–110) names ~30–50 inbox items/day as the sustainable cap; a top-level edit could exceed that in one event. **The grouping in §1 step 5 is the load-bearing mitigation:** the user sees one grouped row, not 30. The depth-4 traversal bound is the secondary mitigation. The Tier-3 default for "consistent verdicts" is the tertiary mitigation — the user does not see the bulk of low-signal proposer outputs unless they explicitly filter Tier 3 in. The synthesis's §Q2 design implications (line 122) commit to "a multi-tier sort, not a single score"; this ADR's behavior depends on that sort working as ADR-0022 specifies. If the inbox sort algorithm in Phase 4 fails to demote consistent verdicts to Tier 3, the volume problem the synthesis names structurally (line 108) becomes acute.
- **The monitor LLM is in the path for the proposer's drift verdicts, which means monitor cost scales with edit frequency.** Per ADR-0005, the monitor's default is Llama 3.3 70B on Groq at ~$0.10–0.20/dev/day at typical traffic. The §1 step 4 proposer produces commit-phase actions; every non-`consistent` verdict goes through the monitor. A team that edits intents heavily — many small edits per day across many top-level intents — will see monitor cost climb proportionally. The ADR-0005 budget envelope assumes typical traffic; if monitor cost climbs above the envelope, the mitigation is to raise the proposer's `consistent`-verdict threshold (so fewer proposals reach the monitor) or to demote `safety_critical` mutations less aggressively (so fewer proposals route to monitor outside the 5% sample). Both mitigations are downstream tuning, not ADR-amendment work.
- **The §4 escape hatch is opt-in.** Users who do not know the affordance exists will experience large pivots as the high-volume version of §1, even when they had a deliberate pivot in mind. The Phase 4 task list amendment includes copy and discoverability work for the affordance — the dialog's keyboard shortcut and the canvas/inbox affordance should be discoverable from the impact-pass grouped row itself ("did you mean to make this change as a scope change? [Yes] [No]"), so users learn the escape hatch by encountering it at the right moment. This pattern is consistent with the synthesis's §Q3 onboarding finding (line 199, "real bounded tasks outperform tutorials"); the affordance is taught in context rather than via a separate tutorial.
- **The `scope_change_active` projection is a new piece of orchestration state.** It is recoverable from `event_log` per the §Schema implications, but it adds a maintenance surface (window expiry, cleanup, debugging when a suppression unexpectedly persists). The Phase 6 hardening territory includes a CLI tool to list active scope changes for diagnostic purposes; that is out of scope here but on the implicit roadmap.
- **The §3b and §3c thresholds (N=5 for code-churn, M=3 for cross-concept failure spread) are guesses.** They are configurable per project, but the defaults are not empirically tuned. The right tuning depends on dogfooding signal that does not exist until Phase 4 is running on the team's own repo. Phase 5's eval harness territory (tech-spec §6 phase 5 line 469) should include precision/recall measurements for the §3 triggers against a labeled set of known-stale and known-current requirements; the labeled set does not exist yet and is itself Phase 5 work. Until then, the thresholds may produce false positives in the digest.

What §5 and §6 add to the consequences picture:

- **The prospective flow turns the AI into a more useful collaborator specifically because it forces the AI to check its own work against the existing constitution before proposing.** This is the difference between an AI that produces plausible-but-conflicting specs and an AI that produces specs that fit the system. The synthesis's framing of structured verification serving a dual purpose — catching human bugs *and* catching AI confabulation (synthesis §"Mental-Model Gap" lines 547–555 on AI confabulation; synthesis §Q1 line 68's "the verifier catches Z" framing in the failure-mode-by-category onboarding; synthesis §Q5 line 406's "verifier outcomes are a *positive* feedback opportunity") — applies directly to the §6 gate. The §6 gate is a verifier on the AI's own authoring, in the same way the obligation verifier is a verifier on the AI's code generation; both prevent the failure mode where the AI produces output that is locally plausible but globally inconsistent. The §6 gate's value is asymmetric: a clean AI proposal pays the gate cost as overhead, but a contradicting AI proposal is prevented from cluttering the inbox, which is the structurally-bounded resource per the synthesis §Q2 finding 1 (lines 108–110). Over the lifetime of a project, the gate's value compounds because the constitution it checks against grows, and an ungated AI would produce more contradictions over time, not fewer.
- **Prospective checks add latency to commit (~500ms–2s for the three checks).** This is the user-perceived cost on every new spec authoring action that lands a node. For a user adding a new intent through the TipTap editor, the commit feels slower by ~1s in the typical case. This is acceptable because (a) new spec authoring is a deliberate, low-frequency action — a user adds intents at a rate of single-digit per day, not per minute; (b) the modal dialog is the rare outcome — most authoring is "no conflicts" and the latency is the only user-perceived cost; (c) the cost compares favorably to the cost of *not* catching the conflict at authoring time, which is the cascade described in the §1 reactive impact pass plus the cognitive cost of reconciling N inbox items. The latency budget should be measured at L1 dogfooding (Phase 3 gate) and tuned in Phase 4 if it exceeds the per-commit acceptability threshold (suggested: ~3s p95, after which the user perceives the editor as unresponsive).
- **The §6 AI-side gate adds cost to every AI-initiated proposal because the proposer has to do additional retrieval and reasoning before surfacing.** Per the §6 cost profile, the gate adds one or more T1 model calls plus one monitor call per AI authoring action. For a high-volume agent path like `intent.extract` running over a fresh codebase that produces dozens of intents in a batch, this stacks. Mitigations are named in §6 (caching, parallel gating, vision cache amortization). The trade is real: the gate makes batch authoring slower and more expensive, but the alternative (no gate, contradictions surface in the inbox) consumes the structurally-bounded inbox-volume budget per the synthesis §Q2 finding 1 (lines 108–110). Inbox volume is the more constrained resource than skill-side compute, so the gate spends compute to preserve volume.
- **The "commit anyway with typed reason" path produces decision nodes that themselves need to be checked against the vision in the future, which is recursive but bounded.** Each option-(c) commit produces a `decision` node with `confidence='asserted'`. These decision nodes are themselves subject to §5's prospective check on subsequent edits (per ADR-0024 §1, asserted nodes that are edited preserve their `asserted` confidence absent demotion). However, the recursion is bounded because (a) decision nodes carry context that is specifically about *resolving* a conflict, so they are unlikely to themselves contradict the vision they were authored to override; (b) §5's vision check excludes `decision` nodes from the vision-collection set (only top-level intents and ADR-derived pillars are collected), so a decision node's content does not become future-vision against which other proposals are judged; (c) the depth of the recursion is one — a decision node about a conflict does not produce its own decision nodes about its own conflicts. The bounded-recursion property is load-bearing; if a future ADR amendment broadens the vision-collection set to include decisions, this property must be re-evaluated.
- **The user-facing UX for the prospective flow introduces a new modal moment (the conflict warning at commit time) that isn't in the current two-surface design.** The existing design (per ADR-0020, ADR-0021, ADR-0022) is canvas + inbox + status-bar, with modal dialogs reserved for `block`-tier override per ADR-0021 §3. The §5 conflict modal is a *third* modal pattern: commit-time, blocking, with a three-option resolution. This needs a Phase 4–5 design pass. The shape of the modal should inherit from ADR-0023's resolver-style side-by-side rendering (which already handles "Yours vs. Theirs" for merges); the three-option affordance is structurally similar to the merge resolver's per-field action set. The dialog's keyboard bindings should be consistent with the rest of the project's keymap. This is downstream UX work; it is named here to ensure the Phase 4 task list reserves room for the design pass, and to make explicit that §5 introduces UX surface area that the existing ADRs do not cover.
- **The §6 gate's pre-inbox rejection path is a silent suppression mechanism that requires the monitor as the only check against gate misuse.** A vision-contradicting AI proposal is rejected before the user sees it; if the §5 step 4 monitor verdict on the conflict-detection output were absent, the gate could silently suppress legitimate AI proposals without recourse. The monitor is the architectural protection against this: it audits the conflict-detection proposer's claim, and a `block` verdict on a rejected proposal routes the proposal through to the inbox with a chevron-overlay indicating monitor disagreement. This is the load-bearing role of the monitor in §6 — without it, the gate would be a credibility hazard for the entire AI-authoring path. The cost is the per-rejection monitor call (already counted in §6's cost profile); the benefit is auditability.
- **The §5 commit-time modal cannot be the user's first IntentGraph experience.** Onboarding (synthesis §Q3 lines 167–248; ADR-0020 §3 Type 4 onboarding-mode hints) puts new users in the inbox first; the commit-time modal would be confusing on first encounter because it presupposes familiarity with the constitution that the user is just learning. The Phase 4 task list amendment should ensure that the prospective check is *active* during onboarding (otherwise contradictions land silently in the new user's first authoring) but the modal copy and option set should adapt for users in the first 30 days per ADR-0024's onboarding-mode pattern — likely with a more verbose explanation of why the conflict was detected and what the three options do.

**Worth flagging here, but not deciding in this ADR:** the question of whether stale-requirement detection eventually graduates from "background digest" to "predictive" — the system flags a requirement as likely-soon-stale based on velocity of nearby changes — is a Phase 5 or v1.1 enhancement, not a Phase 4 commitment. The substrate supports the trajectory: the `event_log` chain plus the PPR machinery plus the proposer can in principle compute a per-node "imminent staleness" score. This ADR does **not** commit to that trajectory; the §3 triggers are reactive (they fire on signals that have already happened), and the predictive variant introduces a class of failure mode (false positives that disrupt work the user has not yet done) that the synthesis's evidence base does not yet inform. A future ADR can revisit when Phase 5 dogfood signal exists.

## Alternatives considered

- **Intent edits do not trigger any automatic propagation; downstream reconciliation is left entirely to the user.** Cheaper to implement: §1 collapses to a single `event_log` row and no further work. No traversal, no proposer, no monitor cost on intent edits. The user, on the next code save that touches an affected descendant, would see the §2 forward-sync flow flag the divergence, and the cumulative effect would eventually surface the impact. **Rejected.** The dogfooding ladder L2 gate (CLAUDE.md L2 gate: ≥80% of symbol-vs-intent drift auto-detected) presupposes that the system is *finding* the drift the user did not yet notice. Pure user-initiated reconciliation requires the user to remember which descendants were affected by an intent edit and to navigate to them; this is exactly the cognitive burden the synthesis's §Q2 finding 2 (line 110, "Sort order for the *first 20 items* is disproportionately important") and §Q2 finding 6 (line 118, "Highest-leverage suggestion is harder than highest-priority") identify as not user-internalizable. The graph data structure makes propagation tractable in IntentGraph in a way it isn't in flat-list inboxes (synthesis line 118); committing to no propagation would forfeit that structural advantage. The cost of automatic propagation is bounded (§Cost profile) and surface-managed (the grouping in §1 step 5). The cost of *not* doing propagation is the failure mode the substrate was designed against — code drifts from intent silently because no automatic process was looking. The choice is not between cheap-and-incomplete versus expensive-and-complete; it is between "the system honors its thesis" versus "the system has the substrate but does not run it."
- **Stale detection is purely user-initiated (a "check for stale requirements" command).** Cheaper to implement: §3 collapses to one MCP tool that the user invokes on demand, returning a list. No scheduled functions, no digest section, no projection maintenance. **Rejected.** The synthesis's §Q2 finding 5 (line 116, "users do not self-monitor fatigue accurately") and the cognitive-depletion literature (§Q2 line 100) jointly establish that users cannot reliably remember to invoke a periodic check. A "check for stale requirements" command becomes a feature that exists but is not run, and stale requirements accumulate until something else (a verifier failure that flips, a code save that mismatches an old intent) surfaces them. The §3a event-driven trigger handles the urgent case; the §3b and §3c scheduled passes handle the slow-burn cases that user-initiated checks miss. The cost is one Inngest scheduled function per cadence (weekly and monthly) plus the digest UI. The protective effect is real: the synthesis's Cross-Cutting Theme #2 (line 621, "Externalize What Cannot Be Internalized") names exactly this pattern — the system tracks what the user cannot.
- **Run the proposer on every intent edit without batching the inbox surfacing.** Cheaper to implement than the grouping; each proposer output gets its own inbox row. **Rejected.** The synthesis's §Q2 finding 1 (line 108) names ~30–50 items/day as the sustainable cap; per-descendant rows on a top-level intent edit blow the cap in one event. The grouping is the load-bearing mitigation; without it, the propagation pipeline produces the exact cognitive-overload failure mode the synthesis warns against.
- **Use PPR for the §1 traversal instead of structural edge-walk.** PPR is the natural retrieval primitive for "what is relevant to this node" (tech-spec §3.7 lines 152–156). **Rejected.** PPR is a *relevance* ranking; the impact pass needs *structural* affectedness. A descendant is affected if it is mechanically downstream of the change via `realizes`/`depends_on`/`syncs_with`/`constrains`, not if it is semantically similar to the changed node. PPR would surface semantically-similar nodes that are not actually affected (false positives) and miss structurally-affected nodes that are not semantically similar (false negatives). PPR is correctly used in §3c for the cross-cutting-violation-spread pass, where the question *is* relevance ("which concepts cluster around this constraint") not structural affectedness.
- **Per-descendant proposer calls in parallel without the depth-4 bound.** Removes the bound; runs the proposer on every transitively-affected node. **Rejected.** Cost grows quadratically in graph density (a high-degree intent edit cascades to its descendants' descendants). The depth-4 bound is conservative — it covers the common case (an intent affects its `realizes` code, the constraints that narrow it, the decisions that reference it, and one hop further) without exploding on densely-connected concept graphs. Configurable per project: a project that wants depth-6 can override; a project that wants depth-2 can override down. The default is calibrated to the synthesis's volume budget plus the typical concept-depth in the team's own dogfood graph.
- **Defer the orchestration commitment to Phase 4 task implementation.** Cheapest of all: each Phase 4 task picks its own behavior. **Rejected.** This is the failure mode the §Context section names: each surface that touches drift reacts to its own trigger in its own way, and the cumulative effect is the architecture's thesis silently failing. The synthesis's §Q2 finding 1 (lines 108–110) names the volume problem as structural; structural problems need structural mitigations, and structural mitigations cannot land as ad-hoc per-task choices. The orchestration commitment must be ADR-level so every Phase 4 task that touches an inbox row consumes the same impact-pass grouping, the same stale-detection digest, and the same scope-change suppression.
- **Make scope-change suppression unconditional (no time window; the user has to manually re-enable propagation).** Simpler — no expiry cron, no projection cleanup. **Rejected.** Forgotten suppressions are a class of bug that is invisible to the user (propagation simply does not happen, and the user cannot tell whether that is because nothing changed or because suppression is silently active). The default 7-day window plus configurable up to 30 days is the synthesis's "confirmation breakpoints at high-risk moments" pattern (line 537–538) inverted: a deliberate quiet window with an automatic resumption point. The user can re-declare scope change if the pivot is still in progress when the window expires; the friction of re-declaration is the protection against silent forever-suppression.
- **Promote stale-detection from background digest to inbox Tier 2 by default.** More aggressive — the user sees stale candidates in the live inbox. **Rejected.** The §3 triggers are slow-changing signals; surfacing them at Tier 2 conflates urgency-now ("a verifier just flipped, fix today") with urgency-eventually ("this requirement may be stale, review when convenient"). The synthesis's §Q2 finding 1 (line 108) identifies the 30–50/day cap as structural; consuming budget on slow-burn signals starves the urgent items. The digest pattern (synthesis §Notification Design line 562, "Aggregate 'this week' summaries for low-priority items") is the right cadence for these triggers.
- **No prospective check; conflicts surface only through the reactive propagation flow after the new spec lands.** Cheaper to implement: §5 collapses entirely; new spec authoring is a normal `node-write.ts` commit with no pause. Conflicts would surface later when the §1 reactive impact pass runs against any subsequent edit that traverses the contradicting node, or when a §3 stale-detection pass picks up the inconsistency. The §6 AI gate would also collapse — AI proposals would land in the inbox without conflict checks, and the user would discover contradictions through the inbox surfacing. **Rejected for two reasons.** First, the reactive-only path means every conflicting commit produces a cascade of inbox items the user has to reconcile, instead of catching the conflict at authoring time when revision is cheap. The synthesis's §Q2 finding 1 (lines 108–110) names the per-day inbox-volume budget as structural; a conflict caught at authoring time costs one modal interaction and zero inbox items, while the same conflict caught reactively costs N inbox items where N is the descendant fan-out of the contradicting node (per §1 step 1's traversal). The asymmetry is large — a single top-level intent that contradicts the vision could fan out to dozens of descendants, each demanding inbox attention to reconcile. Second, **reactive-only doesn't help the AI at all.** AI proposals would land contradictions silently into the inbox until the next propagation pass runs, at which point the user is presented with both the proposal *and* its downstream cascade as separate decisions. This is the failure mode the synthesis names directly: AI confabulation that produces "plausible intent the human didn't actually have" (synthesis §"Mental-Model Gap" lines 549–551) becomes inbox volume that the user must individually adjudicate. The §6 AI-side gate is the substrate-level mitigation for AI confabulation in the authoring path; rejecting prospective checks rejects the gate, and rejecting the gate accepts the confabulation risk as a permanent inbox-volume drain. The cost of the prospective check is real (latency, compute) but bounded; the cost of reactive-only scales with conflict frequency and is unbounded.
- **Prospective conflict detection runs but is purely advisory, never blocking.** The §5 dialog is replaced by a non-modal toast or status-bar indicator: "potential conflict detected; click to investigate." Commits proceed regardless; the user can choose to revisit. Cheaper from a UX-friction standpoint and respects the synthesis's autonomy principle (§Q1 / human-AI teaming literature on the importance of user agency). **Rejected.** Advisory-only means the user has to remember to read the warnings, which the cognitive load research says they won't. The synthesis's §Q2 finding 5 (line 116) is unanimous — "users do not self-monitor fatigue accurately" — and the broader §Q2 cognitive-depletion analysis (line 100) plus the Cross-Cutting Theme #2 ("Externalize What Cannot Be Internalized," line 621) extend that finding to attention generally: an advisory warning surfaced asynchronously is structurally equivalent to no warning, because the user has already moved on to the next task by the time they would have read it. The blocking-with-override pattern (commit anyway with a typed reason per §5 outcome (c)) is the right shape because it forces explicit acknowledgment without removing user autonomy. The CPOE override-reason research (synthesis line 132 around "structured override reason"; ADR-0022 §4) is direct evidence that requiring a typed reason reduces inappropriate overrides without significantly slowing throughput — the friction is calibrated to the protection. Advisory-only would replicate the pure-dashboard-monitoring failure mode the synthesis names (§Adjacent Findings line 541, "Pure dashboard-monitoring … leads to vigilance decrement within ~30 minutes"). The user retains autonomy through option (c); the system retains protection through the modal moment.
